## 一、析构函数基础

### 什么是析构函数

析构函数是对象**"死亡时"自动调用**的函数。当一个对象的生命周期结束，C++ 运行时会自动调用它的析构函数，你无需手动触发。

语法规则很简单：

```cpp
class MyClass {
public:
    ~MyClass() {   // 波浪号 ~ 开头，类名同名，无参数，无返回值
        // 清理工作写在这里
    }
};
```

三点约束：
- 函数名必须是 `~类名`
- **无参数**（也不能重载，一个类只能有一个析构函数）
- **无返回值**（连 `void` 都不写）

### 最简单的例子

```cpp
#include <iostream>

class Resource {
public:
    Resource()  { std::cout << "Resource 创建" << std::endl; }
    ~Resource() { std::cout << "Resource 销毁" << std::endl; }
};

int main() {
    Resource r;   // 构造函数调用
    std::cout << "main 函数执行中..." << std::endl;
    return 0;     // r 离开作用域，析构函数自动调用
}
```

输出：
```
Resource 创建
main 函数执行中...
Resource 销毁
```

析构函数被自动调用了，你什么都不用做。

### 析构函数的核心用途：释放资源

当对象在构造时**申请了某种资源**（堆内存、文件句柄、网络连接……），析构函数就是释放这些资源的正确位置。

```cpp
class Buffer {
public:
    int* data;
    int  size;

    Buffer(int n) {
        size = n;
        data = new int[n];   // 构造时申请堆内存
        std::cout << "分配了 " << n << " 个 int 的空间" << std::endl;
    }

    ~Buffer() {
        delete[] data;       // 析构时释放堆内存
        std::cout << "内存已释放" << std::endl;
    }
};

int main() {
    Buffer buf(100);
    buf.data[0] = 42;
    // 函数结束，buf 自动析构，内存自动释放，不会泄漏
    return 0;
}
```

**如果没有析构函数，`new` 出来的内存就永远不会被释放。** 这就是内存泄漏。

### 什么时候不需要写析构函数

如果你的类**没有持有任何需要手动释放的资源**（没有裸指针、没有文件句柄、没有锁……），就不需要写析构函数。编译器会生成一个默认的空析构函数。

```cpp
class Point {
public:
    double x = 0.0;
    double y = 0.0;
    // 不需要析构函数，double 类型自己会正确销毁
};
```

## 二、对象生命周期（重点）

这是本课最核心的内容。不同的创建方式，决定了对象在哪里存活、何时被销毁。

### 2.1 栈上对象

最常见的方式。对象在函数内声明，存储在调用栈上。

```cpp
void foo() {
    Resource r;         // 进入 foo 时构造
    // ... 使用 r ...
}                       // foo 返回时，r 自动析构
```

**生命周期**：从声明那一行开始，到所在的**作用域（花括号）结束**时自动析构。

```cpp
int main() {
    {
        Resource r1;    // r1 构造
        std::cout << "内层作用域" << std::endl;
    }                   // r1 析构 ← 注意：这里！不是 main 结束
    std::cout << "外层作用域" << std::endl;
}   // main 结束
```

输出：
```
内层作用域
Resource 销毁       ← 内层花括号结束时触发
外层作用域
```

> 💡 花括号控制的不只是变量的可见范围，还决定了栈对象的生死。这是 RAII（模块五会专门讲）的基础机制。

### 2.2 堆上对象

用 `new` 创建的对象存在于堆（heap）上。**堆上的对象不会自动析构**，必须由你手动 `delete`。

```cpp
int main() {
    Resource* p = new Resource();   // 构造
    // ... 使用 p ...
    delete p;                       // 你必须手动调用，析构函数才会执行
    p = nullptr;                    // 好习惯：delete 后立即置空
}
```

`delete` 做了两件事：
1. 调用对象的析构函数
2. 将那块内存归还给操作系统

如果你忘记 `delete`，对象永远不会被析构，内存永远不会被释放——**内存泄漏**。

对于数组形式的 `new`，必须用 `delete[]`：

```cpp
int* arr = new int[100];
delete[] arr;    // 注意是 delete[]，不是 delete
```

`new[]` 配 `delete`，或 `new` 配 `delete[]`，都是**未定义行为**，程序可能崩溃。

### 2.3 全局对象

在所有函数外部声明的对象。

```cpp
Resource globalRes;   // 全局对象

int main() {
    std::cout << "main 开始" << std::endl;
    return 0;
}
```

输出：
```
Resource 创建        ← main 开始之前
main 开始
Resource 销毁        ← main 返回之后
```

**生命周期**：程序启动时构造（早于 `main`），程序结束时析构（晚于 `main` 返回）。

> ⚠️ 多个全局对象之间，构造和析构的顺序**跨编译单元时是不确定的**（同一个 `.cpp` 文件内按声明顺序）。因此要避免全局对象之间互相依赖。

### 2.4 静态局部对象

用 `static` 修饰的局部变量，只初始化一次。

```cpp
void bar() {
    static Resource staticRes;   // 第一次调用 bar 时构造，之后不再重复构造
    std::cout << "bar 被调用" << std::endl;
}

int main() {
    bar();   // staticRes 构造，输出 "bar 被调用"
    bar();   // staticRes 不再构造，输出 "bar 被调用"
    bar();
    // main 结束后，staticRes 才析构
}
```

**生命周期**：第一次执行到声明处时构造，程序结束时析构。这是实现单例模式（Singleton）最简洁的方式之一。

## 三、析构顺序（难点）

析构顺序遵循一个统一规律：**后构造的先析构（LIFO，后进先出）**。

这就像叠盘子：最后放上去的，最先被拿走。

### 3.1 同一作用域内的多个栈对象

```cpp
int main() {
    Resource a;   // 第1个构造
    Resource b;   // 第2个构造
    Resource c;   // 第3个构造
}   // 析构顺序：c → b → a
```

输出：
```
Resource a 创建
Resource b 创建
Resource c 创建
Resource c 销毁
Resource b 销毁
Resource a 销毁
```

### 3.2 继承体系中的析构顺序

（继承会在模块二详细讲，这里先建立一个基本印象。）

```cpp
class Base {
public:
    Base()  { std::cout << "Base 构造" << std::endl; }
    ~Base() { std::cout << "Base 析构" << std::endl; }
};

class Derived : public Base {
public:
    Derived()  { std::cout << "Derived 构造" << std::endl; }
    ~Derived() { std::cout << "Derived 析构" << std::endl; }
};

int main() {
    Derived d;
}
```

输出：
```
Base 构造
Derived 构造
Derived 析构     ← 派生类先析构
Base 析构        ← 基类后析构
```

构造：先基类，再派生类。析构：先派生类，再基类——**严格相反**。

### 3.3 成员对象的析构顺序

类的成员对象在构造时按**声明顺序**初始化，析构时**反序**。

```cpp
class Engine {
public:
    Engine()  { std::cout << "Engine 构造" << std::endl; }
    ~Engine() { std::cout << "Engine 析构" << std::endl; }
};

class Wheel {
public:
    Wheel()  { std::cout << "Wheel 构造" << std::endl; }
    ~Wheel() { std::cout << "Wheel 析构" << std::endl; }
};

class Car {
    Engine engine;   // 声明顺序：1
    Wheel  wheel;    // 声明顺序：2

public:
    Car()  { std::cout << "Car 构造" << std::endl; }
    ~Car() { std::cout << "Car 析构" << std::endl; }
};

int main() {
    Car c;
}
```

输出：
```
Engine 构造     ← 成员按声明顺序构造
Wheel 构造
Car 构造        ← 最后才是 Car 自身的构造函数体
Car 析构        ← Car 的析构函数体先执行
Wheel 析构      ← 然后成员按反序析构
Engine 析构
```

> 📌 析构函数体先执行，然后成员按反序析构，最后基类析构。这个顺序要熟记，多态下的内存安全（L14）和复杂类的设计都依赖这个规律。

## 四、常见错误与陷阱（重点）

这一节的每一条都是真实项目中会遇到的 bug，要逐一记牢。

### ❌ 陷阱一：双重释放（Double Free）

对同一块内存执行两次 `delete`，会导致程序崩溃或堆损坏。

```cpp
Resource* p = new Resource();
delete p;
delete p;   // 崩溃！同一块内存被释放了两次
```

**解决方法**：`delete` 后立即将指针置为 `nullptr`。对 `nullptr` 执行 `delete` 是安全的，什么也不会发生。

```cpp
delete p;
p = nullptr;
delete p;   // 安全，对 nullptr delete 无副作用
```

### ❌ 陷阱二：悬空指针（Dangling Pointer）

指针指向的内存已经被释放，但指针本身还保存着那个地址，继续使用它是**未定义行为**。

```cpp
Resource* p = new Resource();
delete p;
// p 现在是悬空指针，但它仍然存储着原来的地址

p->someFunction();   // 未定义行为：可能崩溃，可能输出垃圾值，可能"正常运行"（最危险的情况）
```

"未定义行为"里最可怕的是**看起来正常运行**——因为那块内存可能暂时还没被覆写，程序侥幸没崩，但下次就不一定了。这类 bug 极难复现和排查。

**解决方法**：同上，`delete` 后置 `nullptr`，之后访问前判断非空。

### ❌ 陷阱三：`new[]` 配 `delete`（类型不匹配）

```cpp
std::string* arr = new std::string[5];
delete arr;    // 错误！只析构了第一个元素，剩余4个没有被析构
               // 同时释放了整块内存，导致未定义行为
```

规则很简单：**`new` 配 `delete`，`new[]` 配 `delete[]`，永远不要混用。**

### ❌ 陷阱四：浅拷贝导致的双重释放

这是本课最隐蔽的陷阱，L05 会专门讲解，这里先见识一下它的危害。

```cpp
class Buffer {
public:
    int* data;
    Buffer(int n) { data = new int[n]; }
    ~Buffer()     { delete[] data; }
    // 没有自定义拷贝构造函数！
};

int main() {
    Buffer a(10);
    Buffer b = a;   // 默认拷贝：b.data = a.data，两个指针指向同一块内存
}   
// 作用域结束：先析构 b，delete[] b.data（同时也是 a.data）
// 再析构 a，delete[] a.data —— 双重释放！程序崩溃
```

现在只需要知道这个问题存在。解决方案是**深拷贝**，即在拷贝构造函数中重新分配内存，而不是共享同一个指针。

### ❌ 陷阱五：在析构函数中抛出异常

```cpp
class Foo {
public:
    ~Foo() {
        throw std::runtime_error("析构时出错");   // 非常危险！
    }
};
```

当栈展开（stack unwinding，即异常传播过程中析构局部变量）时，如果析构函数再次抛出异常，C++ 会直接调用 `std::terminate()` 终止程序。

**原则：析构函数内绝对不能抛出异常。** 如果析构时的操作可能失败（比如关闭文件失败），应当在内部捕获并处理，或静默忽略，决不能让异常逃出析构函数。

```cpp
~FileWrapper() {
    try {
        file.close();
    } catch (...) {
        // 吃掉异常，记录日志，但绝不向外抛
    }
}
```

## 五、完整示例：文件读取器

把本课所有概念综合到一个实际场景里：

```cpp
#pragma once
#include <string>
#include <cstdio>   // FILE*

class FileReader {
public:
    std::string filename;

    FileReader(const std::string& path) : filename(path) {
        fp = std::fopen(path.c_str(), "r");
        if (!fp) {
            std::cerr << "无法打开文件：" << path << std::endl;
        } else {
            std::cout << "文件已打开：" << path << std::endl;
        }
    }

    ~FileReader() {
        if (fp) {
            std::fclose(fp);   // 析构时自动关闭文件
            std::cout << "文件已关闭：" << filename << std::endl;
        }
    }

    bool isOpen() const { return fp != nullptr; }

private:
    FILE* fp = nullptr;
};
```

```cpp
#include "FileReader.h"

void processFiles() {
    FileReader f1("config.txt");   // f1 构造，文件打开
    FileReader f2("data.csv");     // f2 构造，文件打开

    if (!f1.isOpen()) return;      // 提前 return 也没问题：f2、f1 按顺序析构，文件都会关闭

    // ... 处理文件 ...

}   // 作用域结束：f2 先析构（文件关闭），f1 后析构（文件关闭）
    // 无论函数如何退出，文件一定被关闭，不会泄漏文件句柄
```

这就是 RAII 的核心思想：**资源的生命周期绑定到对象的生命周期**，由析构函数负责自动释放，从根本上消除泄漏的可能。

## 六、本课小结

| 知识点 | 核心结论 |
|---|---|
| 析构函数语法 | `~类名()`，无参数，无返回值，不可重载 |
| 栈对象 | 作用域（花括号）结束时自动析构 |
| 堆对象 | 必须手动 `delete`，否则内存泄漏 |
| 全局对象 | main 之前构造，main 之后析构 |
| 静态局部对象 | 首次执行到时构造，程序结束时析构 |
| 析构顺序 | 后构造先析构（LIFO）；成员按声明逆序析构；派生类先于基类 |
| `delete` 后置空 | 防止双重释放和悬空指针 |
| `new[]` 配 `delete[]` | 不可混用，否则未定义行为 |
| 析构函数不能抛异常 | 会导致 `std::terminate()` |

### 作业一：验证析构顺序

这道题的目标是**亲眼看到析构顺序**，而不是写功能代码。

创建一个 `Tracer` 类：

- 构造函数接收一个 `std::string` 参数作为名字，构造时打印 `"[名字] 构造"`
- 析构函数打印 `"[名字] 析构"`

在 `main` 函数中，按照以下结构编写代码，**先自己预测**每一行的输出，再运行验证：

```cpp
int main() {
    Tracer a("a");
    Tracer b("b");
    {
        Tracer c("c");
        Tracer d("d");
    }
    Tracer e("e");
    return 0;
}
```

然后再追加以下实验：

1. 在 `main` 之前定义一个全局的 `Tracer global("global")`，观察它什么时候构造和析构
2. 在某个函数内定义 `static Tracer s("static")`，调用该函数三次，观察静态对象的行为

**目标**：你的预测和实际输出完全一致，说明你真正理解了生命周期。如果有出入，找出原因。

### 作业二：手动管理动态数组

设计一个 `IntArray` 类，封装一段在堆上分配的整型数组，要求：

- 构造函数接收数组大小 `n`，用 `new int[n]` 分配内存，并将所有元素初始化为 0
- 析构函数负责用 `delete[]` 释放内存，并打印一行提示
- 提供以下成员函数：
  - `void set(int index, int value)`：设置指定位置的值，需要做下标越界检查
  - `int get(int index) const`：获取指定位置的值，同样需要越界检查
  - `int size() const`：返回数组大小
  - `void print() const`：打印所有元素

在 `main` 中：
1. 在栈上创建一个 `IntArray`，使用后观察析构时机
2. 用 `new` 在堆上创建另一个 `IntArray`，使用后手动 `delete`，确认析构函数被调用
3. 故意**不** `delete` 堆上的对象（注释掉 delete），用 AddressSanitizer（编译加 `-fsanitize=address`）或 Valgrind 验证内存泄漏确实发生了——如果工具暂时不会用，改用在析构函数里打印来间接验证是否被调用

**核心练习**：`new[]` 与 `delete[]` 的配对，以及堆对象何时/是否被析构。

### 作业三：资源管理类——互斥锁模拟

模拟一个简化版的"锁守卫"（类似标准库的 `std::lock_guard`），理解 RAII 如何用析构函数保证资源释放。

首先实现一个简单的 `Mutex` 类（不用真实的锁，用布尔值模拟）：

```cpp
class Mutex {
public:
    void lock()   { std::cout << "Mutex 已锁定" << std::endl; locked = true; }
    void unlock() { std::cout << "Mutex 已解锁" << std::endl; locked = false; }
    bool isLocked() const { return locked; }
private:
    bool locked = false;
};
```

然后实现一个 `LockGuard` 类：

- 构造函数接收一个 `Mutex&` 引用，立即调用 `mutex.lock()`
- 析构函数调用 `mutex.unlock()`
- 禁止拷贝（暂时可以不管怎么禁，先不写拷贝构造函数就行）

在 `main` 中验证以下两个场景：

**场景一（正常流程）**：

```cpp
Mutex m;
{
    LockGuard guard(m);
    std::cout << "临界区代码执行中..." << std::endl;
}   // guard 析构，锁自动释放
std::cout << "锁是否还持有：" << m.isLocked() << std::endl;
```

**场景二（提前返回）**：

写一个函数 `bool doWork(Mutex& m, bool shouldFail)`，函数内用 `LockGuard` 锁定互斥锁，然后根据 `shouldFail` 参数决定是中途 `return false` 还是正常执行完返回 `true`。

两种情况下，验证函数返回后互斥锁都处于解锁状态。

**思考**：如果不用 `LockGuard`，手动 `lock()/unlock()`，在提前 `return` 的路径上会发生什么？这就是 RAII 解决的核心问题。
